# forge v0.2 — Design Spec

- **Date:** 2026-05-31
- **Status:** Awaiting approval (ready for plan-writing)
- **Predecessor:** [v0.1 design spec](2026-05-26-design.md), v0.1.0 / v0.1.1 shipped
- **Trigger:** Issue #3 — CLI gaps blocking agentic CI debugging + PR lifecycle
- **Author context:** samoore (homelab Forgejo at `git.stevenamoore.dev`)

## Context

Filed by the storyteller dev-agent loop after operating against PR #76. Without log
access from the agent's vantage, CI failures stall until a human pastes them in.
Without PR-state mutations (close, edit base), wrong-target PRs accumulate.

v0.1 nailed the read-side (PR list/view/checks, issue list/view, auth, comment).
v0.2 fills the operational gaps that block end-to-end agent loops:

1. **CI log access** — agents need to see why a check failed without human paste.
2. **PR lifecycle mutations** — close orphaned PRs, retarget wrong-base PRs.
3. **Workflow run discovery** — list runs by branch/status so agents can target them.
4. **--debug HTTP logging** — promised in v0.1 README, deferred from there.

## Forgejo API surface — what was investigated

Probed `git.stevenamoore.dev` (Forgejo 11.0.14 / Gitea-1.22 compatibility) via
swagger.v1.json + live endpoint probes:

| Capability | API exists? | Notes |
|---|---|---|
| `GET /repos/{o}/{r}/actions/tasks` (list runs) | ✅ | Returns `{workflow_runs, total_count}`. Each run has `id` (task id), `run_number`, `name`, `head_branch`, `head_sha`, `status`, `event`, timestamps, `url`. |
| `GET /actions/runs/{id}` or `/tasks/{id}` (single) | ❌ | 404. No single-run resource. |
| `GET .../logs` (any shape) | ❌ | 404 for all probed paths. |
| `POST .../rerun` | ❌ | 404. No rerun API. |
| `POST /actions/workflows/{name}/dispatches` | ✅ | Workflow-dispatch trigger. Deferred to v0.3 per scope decision. |
| `PATCH /repos/{o}/{r}/pulls/{N}` | ✅ | Body `EditPullRequestOption` accepts `state`, `base`, `title`, `body`, `assignees`, `labels`, `milestone`, `due_date`. |

**On-disk logs (workaround for missing API):**

Forgejo persists task logs at:
```
/data/gitea/actions_log/{owner}/{repo}/{id_hex}/{id_decimal}.log.zst
```
Inside the `forgejo` container, where `id_hex = format(task_id, 'x')` (lowercase,
no zero-padding). Compressed with zstd, plaintext + ANSI escapes.

Observed retention: **only failed runs retain logs**; Forgejo purges logs of
successful runs. This is exactly the cohort agents need.

## Section 1 — `forge pr close`, `forge pr reopen`

```
forge pr close <number> [-R owner/repo]
forge pr reopen <number> [-R owner/repo]
```

**Implementation:** `PATCH /repos/{o}/{r}/pulls/{N}` body `{"state": "closed"|"open"}`.

**Output:** One line on success: `Closed PR #N` / `Reopened PR #N`. Exit 0.

**Errors:**
- 404 → `NotFoundError` exit 3 (`pr not found (3)` on stderr)
- 403 → `AuthError` exit 4 (`forbidden (4)`)
- Already in target state → idempotent: re-PATCH succeeds, print success line
- Merged PR + close → Forgejo accepts but is a no-op; do not special-case

**gh parity:** `gh pr close <N>` / `gh pr reopen <N>` — same args, same exit codes.

## Section 2 — `forge pr edit`

```
forge pr edit <number> [-R owner/repo]
              [--base <branch>]
              [--title <text>]
              [--body <text>]
```

**Implementation:** `PATCH /repos/{o}/{r}/pulls/{N}` body containing only the
provided fields. At least one of `--base`/`--title`/`--body` is required (else
`UsageError` exit 2).

**Output:** `Edited PR #N` + a short line per field changed (e.g. `  base: dev → test`).

**Errors:**
- No fields provided → exit 2 with hint
- 404 → exit 3
- 422 (invalid base — branch doesn't exist) → `ValidationError` exit 6 with
  Forgejo's `"message"` field surfaced

**gh parity:** `gh pr edit <N> --base/--title/--body` — same args.

**v0.2 explicit non-goals:** `--add-label`, `--remove-label`, `--add-assignee`,
`--milestone`. The PATCH endpoint accepts them; we defer their CLI surface to
v0.3 to keep v0.2 thin.

## Section 3 — `forge run list`

```
forge run list [-R owner/repo]
               [--branch <name>]
               [--status success|failure|cancelled|...]
               [--workflow <file.yml>]
               [--limit <N>]
               [--json [fields,...]]
```

**Implementation:** `GET /repos/{o}/{r}/actions/tasks?limit=N`. Forgejo's
`limit` defaults to 30, max 50; we expose `--limit` with default 20, max 50.
Filtering by branch/status/workflow happens client-side because the API doesn't
expose these as query params.

**Output (default table):**
```
ID    RUN  STATUS    WORKFLOW    BRANCH                     EVENT         TITLE
161    17  success   test.yml    v0.1.1                     push          release: bump version to 0.1.1
160    17  success   test.yml    v0.1.1                     push          release: bump version to 0.1.1
120     7  failure   test.yml    main                       push          docs: add v0.1 plan
```

Status shown in plain text (no color in v0.2 — color is a v0.3 concern).

**Output (`--json`):**

Translation table `RUN_FIELDS` (in `translate.py`):

| forge JSON | Forgejo source |
|---|---|
| `id` | `id` |
| `runNumber` | `run_number` |
| `name` | `name` |
| `displayTitle` | `display_title` |
| `headBranch` | `head_branch` |
| `headSha` | `head_sha` |
| `status` | `status` |
| `event` | `event` |
| `url` | `url` |
| `createdAt` | `created_at` |
| `startedAt` | `run_started_at` |
| `updatedAt` | `updated_at` |
| `workflowId` | `workflow_id` |

**gh parity:** `gh run list` exists; map shape is similar (gh uses `databaseId`/`displayTitle`/`headBranch`/etc.).
We follow gh's camelCase convention; the `.github_compat_table.md` documents the field-name map.

## Section 4 — `forge run log`

```
forge run log <run-id> [-R owner/repo]
              [--container <name>]
```

**Implementation strategy: on-disk via container exec.**

The Forgejo API exposes no log endpoint on 11.0.14. The only mechanism is reading
the on-disk file from inside the `forgejo` container. To avoid coupling forge to
docker, the mechanism is gated behind explicit user opt-in:

1. `--container <name>` flag, or
2. `FORGEJO_CONTAINER` env var

When neither is set, `forge run log` fails with a clear message:

```
$ forge run log 120 -R samoore/forge
log access requires container exec on the Forgejo host.
Forgejo 11 has no log API; pass --container <name> or set FORGEJO_CONTAINER.
See https://git.stevenamoore.dev/samoore/forge/issues/3 (6)
```

(Exit 6 = `ValidationError` — the user-side config is invalid for the request.)

When set, forge runs:
```
docker exec <container> cat /data/gitea/actions_log/{owner}/{repo}/{id_hex}/{id}.log.zst
```
Pipes the output through python's `zstandard` decompressor in-process. Prints
decoded text to stdout. Exit 0.

**No `docker` binary requirement on the forge install host** — `docker exec`
runs locally on the host where forge is invoked; the user is responsible for
docker access. Spec assumes the typical setup: forge runs on the same host
that runs the Forgejo container. (For remote hosts, the user can wrap forge
in their own SSH.)

**Error: "no log on disk"**

Forgejo only retains logs for failed runs (success runs get purged). When
the `.log.zst` file is missing, surface this clearly:

```
$ forge run log 161 -R samoore/forge --container forgejo
no log on disk for run 161 (probably succeeded — Forgejo only retains failed-run logs) (3)
```
Exit 3 (`NotFoundError`).

**Error: container doesn't exist / docker unavailable** — exit 5 (`ServerError`)
with stderr message from `docker exec`.

**Dependency:** Adds `zstandard>=0.22` to `pyproject.toml` runtime deps.

**gh parity:** `gh run view <id> --log` is the closest analog. We name the
subcommand `log` (noun) rather than `view --log` for v0.2 — simpler CLI surface,
deviation documented in `.github_compat_table.md`.

## Section 5 — `forge pr log`

```
forge pr log <number> [-R owner/repo]
             [--container <name>]
             [--failed-only]
```

**Implementation:** A convenience composite of `run list` + `run log`:

1. Resolve PR # → head SHA via `GET /repos/{o}/{r}/pulls/{N}`
2. `GET /actions/tasks?limit=50`, filter by `head_sha`
3. If `--failed-only` (default `true` in v0.2 — the common case), keep only
   `status=failure`. Otherwise keep all.
4. For each retained task, fetch its on-disk log (same path as §4)
5. Concatenate with per-job header: `===== run #<run_number> "<name>" (id=<id>) status=<status> =====\n`

**Errors:**
- 404 on PR → exit 3
- No matching runs for head SHA → print warning to stderr, exit 0 with empty stdout
  (an agent retry loop reads exit code, doesn't care about empty body)
- Missing `.log.zst` files → annotated in headers as `no log on disk`, continue
  with other jobs. Exit 0 if at least one log fetched; exit 3 if none.

**gh parity:** No direct gh equivalent. `gh pr checks` lists checks but doesn't
fetch their logs. Documented as forge-specific.

## Section 6 — `--debug` HTTP logging

When `--debug` is passed on the top-level group (or `FORGE_DEBUG=1` is set,
already supported in v0.1 for tracebacks), instrument `ForgejoClient._request`
to emit each request and response to stderr:

```
> GET https://git.stevenamoore.dev/api/v1/repos/samoore/forge/pulls/2 (no body)
< 200 OK (1234 bytes, 142ms)
> PATCH https://git.stevenamoore.dev/api/v1/repos/samoore/forge/pulls/2 body={"state":"closed"}
< 200 OK (789 bytes, 88ms)
```

**Implementation:** Pass a `debug: bool` flag into `ForgejoClient.__init__`. The
existing `_request` method wraps the call in `time.perf_counter()` measurement
and emits to stderr if `self._debug`. Auth headers are NOT logged (token must
not leak); body is logged verbatim except for `Authorization` header value
which is redacted to `token <redacted>` if it ever shows up in `kwargs['headers']`.

The CLI dispatcher in `cli/main.py` reads `--debug` from the group and threads
it into every `_build_client(...)` call across pr/issue/auth/run/etc.

## Out-of-scope for v0.2 (deferred to v0.3+)

- `forge workflow run <name>` — workflow_dispatch trigger (issue #3 priority 2 partial)
- Color in `run list` table
- `forge pr edit --add-label/--add-assignee/--milestone`
- Single-run view `forge run view <id>` (no API to back it cleanly)
- HTTP retry logging beyond the request log already in §6
- True streaming log output (we buffer the whole file then print)

## Non-functional commitments carried over from v0.1

- Coverage gate: `pytest --cov-fail-under=85` (unchanged)
- Python: 3.12 + 3.13 matrix CI (unchanged)
- TDD: every new feature has a failing test first
- Test rings: unit (MockTransport), integration (against live `git.stevenamoore.dev` — `RUN_INTEGRATION=1` gated)
- Translation tables (declarative) for any new field shape (see `RUN_FIELDS` in §3)
- Dependency direction: `cli/*` → `client.py`/`translate.py`/`repo.py`/`errors.py`. Never the reverse.

## Acceptance criteria

A scripted end-to-end against `samoore/forge`:

1. `forge pr close 2` → fails (already merged, but should be idempotent — actually exits 0 since PATCH state=closed on merged returns 200)
2. `forge pr edit 2 --title "test: roundtrip via forge"` → exits 0
3. `forge pr edit 2 --title "feat: roundtrip via forge"` → restore
4. `forge run list -R samoore/forge --status failure --limit 5` → table with id, run, branch, sha
5. `forge run list -R samoore/forge --json id,status,headBranch --limit 3` → JSON
6. `forge run log 120 -R samoore/forge --container forgejo` → ~800 lines of log
7. `forge run log 161 -R samoore/forge --container forgejo` → exit 3, "no log on disk"
8. `forge run log 999999 -R samoore/forge` (no --container) → exit 6, "log access requires..."
9. `forge --debug pr view 2` → request lines on stderr, PR view on stdout
