# forge — Design Spec

- **Date:** 2026-05-26
- **Status:** Approved (brainstorming complete; ready for plan-writing)
- **Author context:** samoore (homelab Forgejo at `git.stevenamoore.dev`)
- **Approach chosen:** Monolithic Python CLI with file-layout seams for future library extraction

## Context

Recently migrated from GitHub (`gh` CLI) to a self-hosted Forgejo instance at
`git.stevenamoore.dev`. Many existing scripts, agent slash-commands, and ad-hoc
tools call `gh` and parse its JSON output via `--jq`. These now need to be
rewritten against Forgejo's REST API (Gitea-compatible at `/api/v1/...`). The
hand-written curl recipes that emerged during the cutover (now embedded across
`/opt/projects/storyteller/.claude/commands/*.md`, agent definitions, etc.) are
the "havoc" this tool absorbs.

`forge` is a `gh`-compatible CLI that targets Forgejo. Existing `gh` invocations
get a near-drop-in replacement (`gh pr list -R foo/bar` → `forge pr list -R foo/bar`),
with output shapes that match `gh` closely enough that existing `--jq` filters
keep working with minimal edits.

## Section 1 — Name, repo location, package layout

**Name:** `forge`. Short, memorable, distinct from `gh`; the binary name and
the package name are the same.

**Repo:** `samoore/forge` on `git.stevenamoore.dev` (this repo). Local clone at
`/opt/projects/forge/`, matching the existing `/opt/projects/<name>/` pattern.

**Package layout:**

```
/opt/projects/forge/
├── pyproject.toml              # entry_point: forge = "forge.cli.main:cli"
├── README.md                   # quickstart + bootstrap
├── CLAUDE.md                   # conventions for future Claude sessions
├── .github_compat_table.md     # gh subcommand → forge support matrix
├── src/forge/
│   ├── __init__.py
│   ├── client.py               # ForgejoClient: httpx wrapper, auth, paging
│   ├── translate.py            # Forgejo↔gh JSON shape translation tables
│   ├── repo.py                 # -R / git-remote / FORGEJO_DEFAULT_REPO resolution
│   ├── errors.py               # Typed exception hierarchy
│   └── cli/
│       ├── __init__.py

│       ├── pr.py               # 8 subcommands
│       ├── issue.py            # 6 subcommands
│       ├── gist.py             # 2 subcommands (Forgejo snippets)
│       ├── auth.py             # 2 subcommands
│       ├── run.py              # 4 subcommands (Actions)
│       └── workflow.py         # 3 subcommands
├── tests/
│   ├── conftest.py
│   ├── fixtures/
│   │   ├── forgejo/            # Captured Forgejo API responses
│   │   ├── gh/                 # Captured gh JSON outputs for comparison
│   │   └── capture.py          # Refresh script — runs against live servers
│   ├── test_client.py

│   ├── cli/
│   │   ├── test_pr.py
│   │   └── ...
│   └── live/                   # Opt-in; FORGE_LIVE_TESTS=1
│       └── test_*.py
└── docs/
    └── specs/
        └── 2026-05-26-design.md  # This file
```

**Dependency-direction rule (load-bearing):** `cli/*` may import from
`client.py`, `translate.py`, `repo.py`, `errors.py`. The reverse is forbidden.
Concretely: `client.py`, `translate.py`, `repo.py`, `errors.py` must never
import anything under `cli/`.

This is the seam that lets us mechanically extract `forgejo_client/` as a
separate library later if a second consumer (e.g., agent-runner, storyteller)
needs programmatic access. Today we ship one package. Tomorrow the extraction
is `mv src/forge/{client,translate,repo,errors}.py src/forgejo_client/` and
updating two import lines in `cli/*`. No code or design changes required.

## Section 2 — Auth, instance URL, repo resolution

**Token precedence** (first found wins; rest are ignored):

1. `--token <value>` CLI flag (highest precedence, useful for one-off overrides)
2. `FORGEJO_TOKEN` environment variable
3. `FORGEJO_API_KEY` line in `~/.secrets/forgejo.env` (existing convention,
   reused — `forgejo-create-repo` and other scripts already read this file)

No interactive `forge auth login` flow in v0.1 (deferred — see Out of Scope).
Users provision tokens via the Forgejo web UI and place them in
`~/.secrets/forgejo.env`.

**Instance URL precedence:**

1. `--host <url>` CLI flag
2. `FORGEJO_HOST` environment variable
3. Default: `https://git.stevenamoore.dev`

**Repo resolution** (`-R owner/repo` resolution chain):

1. `-R owner/repo` CLI flag (highest precedence)
2. Current directory's `git remote -v` → parse the `origin` remote, extract
   `owner/repo` if it points at the configured instance host. **Host-mismatch
   validation:** if the remote points at a different host (e.g., `github.com`),
   `forge` errors with `repo: remote 'origin' points at github.com, not the
   configured Forgejo at git.stevenamoore.dev — pass -R explicitly or set
   FORGEJO_DEFAULT_REPO`. This prevents silent cross-instance footguns.
3. `FORGEJO_DEFAULT_REPO` environment variable (last resort, useful for
   scripts that run outside any git directory)

**`forge auth status`:** prints the resolved token source, the instance URL,
the authenticated user (from `/api/v1/user`), and the token's reported scopes.
Exits 0 if reachable + authenticated, 4 if auth fails, 5 if unreachable.

**`forge auth git-credential`:** implements git's credential-helper protocol so
`git push` / `git pull` to `git.stevenamoore.dev` URLs can use forge's stored
token. Usage: `git config --global credential.https://git.stevenamoore.dev.helper
"!forge auth git-credential"`. Reads `get`/`store`/`erase` from stdin per the
git-credential protocol; only `get` is implemented (store/erase are no-ops that
exit 0, since forge's tokens are managed out-of-band).

## Section 3 — Command surface (25 subcommands across 6 nouns)

All commands follow the pattern `forge <noun> <verb> [args] [flags]`.

### `forge pr` (8 subcommands)

| Subcommand | Purpose | Forgejo API |
|---|---|---|
| `list` | List PRs on a repo, with filters | `GET /repos/{owner}/{repo}/pulls` |
| `view <num>` | Show PR details (title, body, state, head, base, labels) | `GET /repos/{owner}/{repo}/pulls/{index}` |
| `create` | Open a new PR | `POST /repos/{owner}/{repo}/pulls` |
| `merge <num>` | Merge a PR (handles `{"Do":"merge"}` capital-D quirk) | `POST /repos/{owner}/{repo}/pulls/{index}/merge` |
| `checks <num>` | Show CI status for the PR's head commit | `GET /repos/{owner}/{repo}/commits/{sha}/status` |
| `comment <num>` | Add a comment | `POST /repos/{owner}/{repo}/issues/{index}/comments` |
| `edit <num>` | Edit title/body/state | `PATCH /repos/{owner}/{repo}/pulls/{index}` |
| `ready <num>` | Mark draft PR as ready for review | `POST /repos/{owner}/{repo}/pulls/{index}` with `draft: false` |

### `forge issue` (6 subcommands)

| Subcommand | Purpose | Forgejo API |
|---|---|---|
| `list` | List issues. **Adds `&type=issues`** to filter out PRs (Forgejo's `/issues` endpoint returns both unless filtered). | `GET /repos/{owner}/{repo}/issues?type=issues` |
| `view <num>` | Show issue details | `GET /repos/{owner}/{repo}/issues/{index}` |
| `create` | Open a new issue. **Labels-as-integer-IDs:** Forgejo requires integer label IDs in the create payload; `forge` accepts label names from `--label foo` and resolves them via `GET /repos/{owner}/{repo}/labels`. | `POST /repos/{owner}/{repo}/issues` |
| `close <num>` | Close an issue | `PATCH /repos/{owner}/{repo}/issues/{index}` with `state: closed` |
| `reopen <num>` | Reopen a closed issue | `PATCH /repos/{owner}/{repo}/issues/{index}` with `state: open` |
| `comment <num>` | Add a comment | `POST /repos/{owner}/{repo}/issues/{index}/comments` |

### `forge gist` (2 subcommands)

Forgejo has no first-class gist concept; **convention:** a dedicated repo
named by `FORGEJO_GIST_REPO` env var (e.g., `samoore/gists`) acts as the gist
store. Each file is a gist. Required env var; `forge gist *` errors at exit 2
if unset.

| Subcommand | Purpose |
|---|---|
| `create` | Create a file in `$FORGEJO_GIST_REPO` |
| `list` | List files in `$FORGEJO_GIST_REPO` |

### `forge auth` (2 subcommands)

| Subcommand | Purpose |
|---|---|
| `status` | See Section 2 |
| `git-credential` | See Section 2 |

### `forge run` (4 subcommands — Forgejo Actions)

| Subcommand | Purpose | Forgejo API |
|---|---|---|
| `list` | List recent workflow runs | `GET /repos/{owner}/{repo}/actions/tasks` |
| `view <id>` | Show run summary and per-job status | (composed from tasks + jobs endpoints) |
| `watch <id>` | Poll a run until terminal state; tail logs | (polling loop) |
| `rerun <id>` | Trigger a re-run | `POST /repos/{owner}/{repo}/actions/runs/{id}/rerun` |

### `forge workflow` (3 subcommands)

| Subcommand | Purpose |
|---|---|
| `list` | List `.forgejo/workflows/*.yml` and `.github/workflows/*.yml` files |
| `view <name>` | Print a workflow file's contents |
| `run <name>` | Dispatch a `workflow_dispatch` run |

### Out of scope for v0.1+

| Excluded | Why |
|---|---|
| `forge api <path>` (raw passthrough) | If you want raw, use `curl`. forge's value is the translation layer; passthrough undermines that. |
| `forge browse` | Trivial wrapper around `xdg-open <repo URL>`; not worth the surface area. |
| `forge auth login` (interactive token-acquire) | Forgejo's web UI is the canonical way to mint tokens; replicating an interactive flow risks token mishandling. |
| `forge repo` (clone, fork, view) | `git clone` already works against Forgejo URLs; nothing to wrap. |
| `forge release` | No current scripts use it; defer to demand. |
| `forge label`, `forge milestone` | Same — defer to demand. |
| Aliases (`gh alias` equivalent) | Shells already have aliases. No new mechanism needed. |
| Template (`gh ... --template`) | `--jq` is sufficient. Two output-templating systems is one too many. |

## Section 4 — JSON shape translation

**Decision:** forge translates Forgejo API responses into `gh`-compatible JSON
shapes. This lets existing `--jq` filters in user scripts keep working with
minimal edits.

**Translation table pattern** (declarative per-resource dict):

```python
PR_FIELDS: dict[str, str | Callable[[dict], Any]] = {
    "number":       "number",
    "title":        "title",
    "state":        lambda p: _pr_state(p),
    "headRefName":  "head.ref",
    "headRefOid":   "head.sha",
    "baseRefName":  "base.ref",
    "createdAt":    "created_at",
    "isDraft":      "draft",
    "url":          "html_url",
    "author":       lambda p: {"login": p["user"]["login"]},
    "labels":       lambda p: [{"name": l["name"], "color": l["color"]}
                                for l in p.get("labels", [])],
}

def _pr_state(p: dict) -> str:
    if p.get("merged"):
        return "MERGED"
    return p["state"].upper()
```

- **String values** are dot-paths into the Forgejo response (`"head.ref"` →
  `forgejo_pr["head"]["ref"]`).
- **Callable values** receive the full Forgejo response and return the value.
  Use for any non-trivial transform (state collapsing, nested object reshaping,
  enum case changes).
- One table per resource type: `PR_FIELDS`, `ISSUE_FIELDS`, `RUN_FIELDS`, etc.

**`--json <fields>` flag:** validates requested fields against the resource's
translation table at parse time. Unknown field → exit 2 with
`unknown field: <name> — available: <comma-separated list>`. Prevents the
silent "wrong field name" failures that plague gh users today.

**`--jq <filter>` flag:** shells out to the system `jq` binary, piping the
translated JSON in via stdin. No embedded jq library — keeps the dependency
surface small and matches `gh`'s actual behavior (it also shells out).

**`--template` flag:** **not implemented** in v0.1+. `--jq` is sufficient;
multiple templating systems is a complexity tax with no payoff.

**Default output (no `--json`):** tab-separated columns chosen per subcommand.
Examples:
- `pr list` → `NUMBER TITLE BRANCH STATE`
- `issue list` → `NUMBER TITLE STATE LABELS`
- `run list` → `ID NAME STATUS HEAD_BRANCH STARTED`

**Snapshot tests:** for every resource type, a captured Forgejo response
fixture + a captured gh response fixture; the test asserts that
`translate.pr_to_gh(forgejo_fixture)` is structurally equal to the gh fixture.
Fixtures live at `tests/fixtures/forgejo/*.json` and `tests/fixtures/gh/*.json`.
Refresh via `tests/fixtures/capture.py` (see Section 6).

## Section 5 — Error handling

**Exit codes** (mirroring `gh`'s contract so existing scripts that check `$?`
keep working):

| Code | Meaning | Triggers |
|---|---|---|
| 0 | Success | Normal completion |
| 1 | Generic error | Unexpected exception, jq filter execution failure |
| 2 | Usage error | Missing required flag, unknown subcommand, unknown `--json` field |
| 3 | Not found | HTTP 404 (repo, PR, issue, gist, workflow, run not found) |
| 4 | Authentication / authorization | HTTP 401, 403, missing token, insufficient scopes |
| 5 | Server error | HTTP 5xx, network failure (DNS, connection refused, timeout) |
| 6 | Validation error | HTTP 422 (e.g., PR base ≠ head, invalid label name) |

**Stderr format** — one line, prefix-tagged, no traceback in normal mode:

```
forge pr view: not found (404): pull request 42 does not exist in samoore/storyteller
forge pr create: validation error (422): base branch 'main' must differ from head branch 'main'
forge issue list: auth failed (401): token rejected — run 'forge auth status' to check
forge run watch: server error (500): https://git.stevenamoore.dev/api/v1/repos/.../tasks/12
```

Format: `forge <noun> <verb>: <category> (<http-or-internal-code>): <detail>`.
Detail comes from Forgejo's `message` field when present, otherwise synthesized
from the HTTP status. Single-line so scripts can `2>&1 | grep` reliably.

**Forgejo error-shape handling:** Forgejo returns errors as
`{"message": "...", "url": "..."}` for most failures, and sometimes
`{"message": "...", "errors": ["...", "..."]}` for validation. `client.py` has
one `_raise_for_response()` that unpacks both shapes and constructs the
appropriate typed exception:

```python
class ForgeError(Exception):              # base; exit code 1
class UsageError(ForgeError): code = 2
class NotFoundError(ForgeError): code = 3
class AuthError(ForgeError): code = 4
class ServerError(ForgeError): code = 5
class ValidationError(ForgeError): code = 6
```

`cli/main.py` wraps top-level dispatch in a try/except that catches
`ForgeError`, prints the formatted message to stderr, and `sys.exit(e.code)`.
Any other exception falls through to a generic handler that prints
`forge: internal error (1): <type>: <message> — run with --debug for traceback`
and exits 1.

**`--debug` / `FORGE_DEBUG=1`:** enables full Python traceback on any error,
plus an httpx request/response log to stderr (method, URL, status, response
time, redacted Authorization header). Off by default.

**Retries:** one retry with 1s backoff on `5xx` and on `httpx.ReadTimeout`.
**No retry on 4xx** — those are deterministic. `--no-retry` flag disables.
Watch loops (`pr checks --watch`, `run watch`) have their own polling logic
and bypass the retry layer.

**Rate limiting:** Forgejo has no documented rate-limiter on self-hosted by
default. If a `429` is returned, treat as `ServerError` and honor the
`Retry-After` header on the single retry (capped at 30s; longer values fail
and let the caller decide).

## Section 6 — Testing strategy

**Ring 1 — Pure unit** (`tests/test_translate.py`, `tests/test_repo_resolution.py`,
`tests/test_errors.py`): no HTTP, no filesystem outside `tmp_path`. Translation
tables exercised against captured fixtures. Repo resolution tested with mocked
`git remote -v` and env-var combinations. Fast, deterministic, run on every
commit.

**Ring 2 — Mocked HTTP** (`tests/test_client.py`, `tests/cli/test_*.py`):
`httpx.MockTransport` injected via a `forge_client` pytest fixture. Each test
stubs specific URL+method combos, asserts request shape (path, query, headers,
body) and response unpacking. CLI tests use click's `CliRunner` with the same
mock transport — testing dispatch + flag parsing + output formatting, not
HTTP.

**Ring 3 — Live integration** (`tests/live/test_*.py`, **opt-in**): hits a
real Forgejo. Enabled only when `FORGE_LIVE_TESTS=1` and both
`FORGEJO_HOST` + `FORGE_LIVE_REPO` are set. Each test creates its own
throwaway artifact, exercises forge against it, cleans up. CI does not run
these — they exist for fixture refresh and post-upgrade API-drift detection.

**Fixture capture script** (`tests/fixtures/capture.py`): given env vars
specifying a live Forgejo + a target repo/PR/issue, hits the API and dumps
responses to `tests/fixtures/forgejo/*.json`. The matching `gh` side is
captured against a GitHub repo (or hand-curated where Forgejo and GitHub
diverge). Re-run when Forgejo's response shape changes; output is committed
and reviewed in diff.

**What we deliberately do not test:**

- `gh`'s own behavior. We assert our output matches captured gh output; we
  don't re-derive gh's logic.
- The httpx library. Trust its HTTP semantics.
- Forgejo's API contracts. Pin to specific shapes via fixtures.

**Coverage posture:**

| Module | Target |
|---|---|
| `translate.py` | ≥95% (this is the heart of the gh-compat promise) |
| `repo.py`, `errors.py` | ≥90% (small, dense, high-impact) |
| `client.py` | ≥75% (HTTP edge cases hard to cover meaningfully without live server) |
| `cli/*` | Happy-path + one error path per subcommand |

`pytest --cov=forge --cov-fail-under=85` gates CI. Per-module targets are
aspirational, not gates.

**CI surface** (`.forgejo/workflows/test.yml`, single file):

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { python-version: ["3.12", "3.13"] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: ${{ matrix.python-version }} }
      - run: pip install -e ".[dev]"
      - run: ruff check src/ tests/
      - run: pytest --cov=forge --cov-fail-under=85
```

## Section 7 — Install & rollout

**Bootstrap sequence (one-time):**

```bash
# Step 1 — repo already exists at samoore/forge on Forgejo

# Step 2 — local scaffold (driven by writing-plans skill)
cd /opt/projects && git clone <repo-url> forge && cd forge

# Step 3 — install onto PATH via pipx, editable so code changes are immediate
pipx install -e /opt/projects/forge
pipx ensurepath   # idempotent

# Step 4 — smoke test
forge auth status
forge pr list -R samoore/storyteller
```

Editable install means `git pull` is sufficient to update; no
`pipx upgrade` rituals.

**Coexistence with `gh`:** both binaries on PATH, separate configs, no
aliasing or routing. Scripts that hit GitHub stay on `gh`; scripts that hit
the homelab Forgejo move to `forge`. Per-script choice.

| Tool | Token source |
|---|---|
| `gh` | `~/.config/gh/hosts.yml` |
| `forge` | `--token` → `FORGEJO_TOKEN` → `~/.secrets/forgejo.env` |

**Migration plan** (opportunistic, not atomic):

| Surface | Approach |
|---|---|
| Slash commands in `/opt/projects/storyteller/.claude/commands/*.md`, parallel autonomous-tree files | Replace `curl -H "Authorization: token..." https://git.stevenamoore.dev/api/v1/...` with `forge <subcommand>` calls. Most-used commands first. |
| Bash scripts at `~/.local/bin/forgejo-*` | Leave alone for now. Migrate only when editing for unrelated reasons. |
| New scripts | Use `forge` from the start. |

No flag-day. No deprecation warnings. Old curl recipes keep working until
individually swapped.

**Versioning & releases:**

| Version | Scope | Acceptance |
|---|---|---|
| **v0.1** | `auth`, `pr` (list, view, create, merge, checks, comment), `issue` (list, view, create, close, comment) | One real storyteller slash-command migrated end-to-end |
| **v0.2** | `run`, `workflow`, full `pr`/`issue` surfaces (edit, reopen, ready) | Forgejo Actions run-watch from CLI replaces manual log-decompress |
| **v0.3** | `gist`, `auth git-credential`, `--jq` polish | Storyteller fully migrated; curl-translation tables in CLAUDE.md files deleted |

Tags on the forge repo; no PyPI publishing (instance-specific by nature).

**Docs in the forge repo:** `README.md`, `.github_compat_table.md`, `CLAUDE.md`.
No man pages, no separate docs site.

## Acceptance criteria for v0.1

1. `pipx install -e /opt/projects/forge` succeeds; `forge --version` prints
   the version.
2. `forge auth status` against `git.stevenamoore.dev` exits 0 with the
   authenticated user printed.
3. `forge pr list -R samoore/storyteller` returns at least one PR (or empty
   list) with no errors; output is tab-separated by default and matches
   `gh`-style JSON when `--json number,title,state` is passed.
4. `forge pr view <num>` displays a real PR's details; `--json` outputs match
   captured `gh` fixtures structurally.
5. `forge issue create -R samoore/<test-repo> --title "..." --body "..."`
   creates an issue and prints its URL.
6. `forge pr merge <num>` merges a real test PR (handles the `{"Do":"merge"}`
   quirk).
7. One existing storyteller slash command is migrated from curl to forge
   end-to-end, with identical behavior.
8. Test suite: `pytest --cov=forge --cov-fail-under=85` passes locally and
   in CI.

## Open questions / explicit deferrals

- **Interactive `forge auth login`:** deferred. v0.1 users provision tokens
  manually via Forgejo web UI.
- **PyPI publishing:** not planned. Re-evaluate if a second consumer needs
  programmatic install.
- **Library extraction (`forgejo_client/`):** not planned for any milestone.
  The dependency-direction rule in Section 1 preserves the option; trigger
  the extraction when a second consumer materializes, not before.
- **Caching layer (HTTP-level cache):** not in scope. Add if performance
  becomes a real problem; premature optimization otherwise.
- **`forge api` raw passthrough:** explicitly excluded. Revisit only if a
  specific need surfaces that can't be served by adding a proper subcommand.

## What this spec does not cover

This is the design. It is not the implementation plan. The next step
(handed off to the `writing-plans` skill) produces a step-by-step plan with
ordered tasks, file-creation sequence, and per-task acceptance checks. This
spec is the authoritative input to that plan.
